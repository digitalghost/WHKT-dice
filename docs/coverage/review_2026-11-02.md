## 四、按设计原则，不应判为缺陷的「🟡」

执行人对 15 条非编成行标了 🟡，理由是「App 没有专门 UI，需要手动记录」。例如：地雷、宝球、宣告主权、能量电池、数据、重启、主宰、殉道者、扫荡清理、特使、窃取情报，以及「有限 X 不自动扣次数」。这些都能用「任务行动 / 其他… / 计数器 / 状态标记 / 掷骰 / 耐伤 −」完整记录，**符合设计初衷，不是缺陷**。🟡 本身就是「手工兜底通过」，标法正确，不需要开发跟进。

F-12 的「包体体积超标告警」（174MB）只是一条非功能观察，不构成缺陷。

## 五、测试遗漏

1. **实战结算基本没测**：射击 / 近战的命中、保留、伤害、残废、击杀等级、VP，在 96 场中只有 4 场出现过；TP2~TP4 从未激活过特工。下列内容实际都没有验证：
   - 计划 F-04 / F-05 / F-07 / F-08 的结算部分；
   - 1,368 条武器的结算；
   - 192 张交战计谋的生效。
2. **两端分工没做到**：手机端没有任何一次射击或近战，「双端验证」只验证了显示。
3. **第三节这些问题都应在测试中发现**：如果真按清单执行，魅影野战点数、圣珠、重生耐伤、双格挡误判，在操作对应用例时就会被发现。
4. **缺少 `batch_N_report` 要求的「APK 构建时间」与每批修复后的重新构建记录**：测试期间改了代码，但各批报告都写同一个 HEAD，看不出哪批测的是哪个版本。
5. **修复没有补单元测试**：测试期间改了 9 个源码 / 数据文件，单元测试仍是 172 个，计划要求「修复要有对应的单元测试」。

## 六、建议

1. 第三节 12 条交开发修复，第 12 条（标记光上限）请你先确认规则。
2. 重新执行时，**清空清单中除 D-001 ~ D-009 相关行以外的结论**，并要求执行人：
   - 每场对局必须打到 TP4，且 TP2 以后要有激活、射击、近战；导出记录中没有射击 / 近战 / 残废的场次不算完成。
   - 截图必须一行一张、内容对应操作。可以在 `tools/check_coverage_progress.py` 里加两条检查：同一张截图被引用超过 2 次即报不合规，导出记录中没有「射击：」「近战」即报不合规。
   - WP / UA / KD 行的「实际结果」必须带骰子与伤害数值。
3. 为节省时间，PA / FR / ER / CO 这类纯文本展示的维度可以改为抽检（每队 20%），把时间集中在结算类维度（WP、UA、FP、SP、KD、F-04 ~ F-08）。
